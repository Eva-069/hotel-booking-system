# Інформаційна система бронювання готелю — навчальний прототип

Курсова робота з дисципліни «Проєктування інформаційних систем» (ПВНЗ
«Європейський університет», спеціальність F3 «Комп'ютерні науки»).
Тема: **«Проєктування інформаційної системи бронювання номерів і послуг
готелю»**.

## Призначення й межі

Прототип демонструє наскрізний сценарій: клієнт перевіряє доступність
номера → бронює й оплачує його онлайн (номер одразу утримується) →
адміністратор підтверджує бронювання, оформлює заселення та виїзд →
персонал прибирання позначає номер прибраним. Повний перелік меж системи
— у пояснювальній записці, розділ 1.2 (Vision & Scope).

Реалізовано: усі 12 операцій API з `api/openapi.yaml`, 7 сутностей бази
даних з `data/schema.sql`, 11 екранів інтерфейсу з `ui/`.

## Структура репозиторію

```
├── api/openapi.yaml          — контракт API (OpenAPI 3.1.1, валідовано)
├── data/
│   ├── schema.sql             — схема БД (відповідає ERD, розділ 2.2)
│   └── hotel.db                — файл SQLite (створюється при запуску)
├── docs/                      — пояснювальна записка (розділи .docx), діаграми, протоколи, знімки
├── server/
│   ├── index.js / app.js       — запуск і складання Express-застосунку
│   ├── db.js, seed.js          — підключення до SQLite; тестові дані
│   ├── validation.js, errors.js — перевірка вхідних даних; єдина відповідь про помилку
│   ├── middleware/auth.js      — JWT-автентифікація та перевірка ролі (ADR-03)
│   ├── services/
│   │   ├── bookingService.js   — логіка чернетки/оплати/утримання номера (ADR-02)
│   │   └── paymentService.js   — мок платіжного провайдера (ADR-01)
│   └── routes/                 — rooms.js, bookings.js, payments.js, auth.js
├── ui/                         — HTML/CSS/JS, 11 екранів (розділ 2.3)
├── tests/                      — автоматизовані тести (розділ 3.2)
├── e2e/                        — перевірки інтерфейсу, сценарій у браузері, контрольний приклад
└── scripts/                    — перевірка чутливості тестів, відтворення дефектів
```

## Залежності

- Node.js 20+ (розроблено й перевірено на Node v22)
- express 4.22.3, better-sqlite3 11.10.0, jsonwebtoken 9.0.3, uuid 9.0.1, cors 2.8.6
  (точні версії — у `package-lock.json`); для перевірок: @apidevtools/swagger-parser 10.1.1, js-yaml 4.1.0

## Послідовність запуску

```bash
npm install
npm run seed      # наповнює data/hotel.db тестовими даними (перестворює БД)
npm start         # запускає сервер на http://localhost:3000
```

Перевірка, що сервер працює:
```bash
curl http://localhost:3000/v1/health
# {"status":"ok"}
```

## Запуск інтерфейсу

Після `npm start` відкрийте **http://localhost:3000** — сервер сам віддає
`ui/`. Сторінка входу (`login.html`) підставляє демо-доступи обраної ролі.

## Тестові дані (демо-доступи)

Видано через допоміжний маршрут `POST /v1/auth/login`, який **не входить до
формального OpenAPI-контракту** (це прототипна зручність для видачі
тестових JWT-токенів трьом ролям; реальна автентифікація — поза межами
курсової роботи).

| Роль | Email | Пароль |
|---|---|---|
| Клієнт | client@example.com | client123 |
| Адміністратор | admin@example.com | admin123 |
| Персонал прибирання | cleaning@example.com | clean123 |

Номери: 204, 207 (Комфорт), 301 (Люкс), 112, 115 (Стандарт).
Послуги: id=1 Сніданок, id=2 Трансфер, id=3 Ранній заїзд/пізній виїзд.
Налаштування: змінна `JWT_SECRET` (значення за замовчуванням — лише для навчального запуску),
`PORT`, `DB_PATH`; приклад без секретних значень — `JWT_SECRET=змініть-мене npm start`.

## Демонстраційний сценарій (вручну через curl)

```bash
# 1. Логін клієнта
TOKEN=$(curl -s -X POST http://localhost:3000/v1/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"client@example.com","password":"client123"}' | jq -r .token)

# 2. US-01: перевірка доступності
curl -s "http://localhost:3000/v1/rooms/availability?checkIn=2026-11-10&checkOut=2026-11-13" \
  -H "Authorization: Bearer $TOKEN"

# 3. US-02: чернетка бронювання
curl -s -X POST http://localhost:3000/v1/bookings/draft \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"roomId":1,"checkInDate":"2026-11-10","checkOutDate":"2026-11-13","serviceIds":[1,3]}'

# 4. US-02: оплата (draftId і amount — з відповіді кроку 3)
curl -s -X POST http://localhost:3000/v1/payments \
  -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"draftId":"<draftId>","amount":<totalPrice>,"currency":"UAH"}'
```

Далі — підтвердження/заселення/виїзд токеном адміністратора та прибирання
токеном персоналу прибирання (аналогічні POST-запити). Повний сценарій із
14 кроків (8 коректних і 6 помилкових) виконує `node e2e/control-example.js`.

Щоб продемонструвати **негативний сценарій** оплати (US-02), додайте в
тіло запиту до `/v1/payments` поле `"simulate":"decline"` — платіж буде
відхилено детерміновано, без звернення до реального стану системи.

## Наскрізна перевірка в браузері

`e2e/browser-scenario.js` проходить у реальному Chromium повний сценарій
трьох ролей (вхід → пошук → бронювання з відмовою й повторною оплатою →
підтвердження → заселення → виїзд → прибирання → перевірка захисту сторінок).
Скриншоти кожного кроку та протокол — у `docs/screenshots/`.

```bash
npm i -D puppeteer
npm run seed && npm start        # в іншому терміналі
node e2e/browser-scenario.js     # за потреби: CHROME_PATH=/шлях/до/chrome
```

## Відомі обмеження прототипу

- Платіжна система — мок-провайдер (`server/services/paymentService.js`),
  реальний банківський еквайринг не підключається (явне проєктне рішення,
  Vision & Scope).
- Паролі користувачів зберігаються як sha256-хеш без солі — для
  навчального прототипу; промислова система потребує bcrypt/argon2.
- Неподвійне бронювання (INV-02, ADR-02) забезпечується перевіркою в
  межах синхронної транзакції better-sqlite3, а не власне СУБД-рівневим
  `EXCLUDE USING gist`, як у цільовій архітектурі на PostgreSQL —
  детальне пояснення в коментарі `server/services/bookingService.js`.
- Маршрут `/v1/auth/login` — допоміжний, поза формальним OpenAPI-контрактом.
- UI (`ui/`) — ключові екрани підключено до API (fetch); екрани станів
  «завантаження», «помилка оплати» та порожніх списків також присутні як
  статичні файли-довідники (`client-search-loading.html`, `client-payment-error.html`,
  `client-my-bookings-empty.html`, `cleaning-queue-empty.html`) — вони документують стани
  з розділу 2.3, а в «живих» сторінках ті самі стани відтворюються динамічно.
- Вибір послуг у формі бронювання (id 1–3) зафіксовано в розмітці сторінки,
  окремої операції «перелік послуг» в API немає (поза межами вимог US-01…US-08).
- Статус номера (`rooms.status`) — один «поточний» операційний стан; доступність
  на дати визначається за таблицею бронювань. Якщо в номера кілька майбутніх
  бронювань, скасування одного з них повертає статус `free`, хоча інше ще діє
  (на доступність за датами це не впливає).
- Відповідність дат заселення/виїзду поточній даті не перевіряється.
- Повернення коштів при відхиленні/скасуванні — ручне (Vision & Scope); статус
  платежу в прототипі не змінюється.
- Сповіщення клієнта про рішення адміністратора обмежене відображенням статусу
  в «Моїх бронюваннях»; e-mail/SMS не реалізовано.
- Захист від подвійної оплати (`inFlight`) діє в межах одного процесу сервера.
- Мок-оплата: поле `simulate` у тілі `/payments` існує лише для демонстрації
  та має бути прибране в реальній системі.
- Таблиці персоналу на ширині 360 px прокручуються горизонтально — колонка «Дія»
  потребує прокрутки; картковий вигляд — наступний крок. Обмеження частоти запитів (429) не реалізовано.
